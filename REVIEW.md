# Ревью исходного MVP «Что приготовить?»

Этап 2. Разбор подготовлен с помощью Codex для совместной проверки с автором проекта. Ссылки ведут на коммит `b4d4f90` ветки `mvp`. Задачи и порядок исправления собраны в [бэклоге](TODO.md).

## Критические

<a name="r01"></a>

### R01. Старый адрес рецепта может указывать на другой рецепт

После удаления рецепта с наибольшим ID SQLite может выдать этот ID снова. На пустой временной базе «Старый» получил ID 1. После его удаления рецепт «Новый» тоже получил ID 1, а запрос по старому адресу открыл «Новый». Это критично для удаления из двух вкладок. В старой вкладке подтверждение показывает название со старой карточки, а запрос удаляет запись по ID. Пользователь может подтвердить удаление одного рецепта и потерять другой. [Первичный ключ рецепта](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/models.py#L24-L30) · [Подтверждение и запрос удаления](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L102-L109)

**Предложение.** Включить для таблицы рецептов SQLite `AUTOINCREMENT`. При обновлении существующей базы перенести записи с сохранением ID и связей. Добавить тест на последовательность «создать → удалить → создать». Новый ID должен отличаться от старого, а старый адрес должен возвращать 404.

## Важные

<a name="r02"></a>

### R02. Подбор загружает весь каталог рецептов

При запросе подбора сервер читает все рецепты вместе с ингредиентами и преобразует каждый рецепт в словарь. Только затем функция подбора исключает рецепты без совпадений. На временной базе из семи рецептов выбор одного продукта «Молоко» загрузил семь объектов `Recipe`. В ответ попали только «Омлет» и «Блины». Это лишняя работа, объём которой растёт с каталогом. [Запрос и преобразование](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/main.py#L139-L145) · [Отсев рецептов](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/matching.py#L11-L17)

**Предложение.** Отбирать запросом SQL рецепты, у которых есть хотя бы один выбранный продукт. Для каждого отобранного рецепта загружать **полный** состав. Он нужен для расчёта процента и списка недостающих продуктов. Проверить равенство результатов на одной базе и отдельно сравнить число загруженных рецептов.

<a name="r03"></a>

### R03. Имя файла базы с вопросительным знаком обрезается

Путь `DATABASE_PATH` подставляется в текст URL подключения. В проверке с именем `ужин?пятница.db` приложение создало файл `ужин`. Две разные конфигурации с одинаковой частью имени до `?` могут открыть одну базу. [Построение URL подключения](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/database.py#L13-L18)

**Предложение.** Передавать путь отдельным аргументом `database` в `URL.create("sqlite", ...)`. В тесте создать две базы с общим началом имени и проверить, что запись из одной отсутствует в другой.

<a name="r04"></a>

### R04. Swagger описывает другой формат ошибки 422

Для `POST /api/matches` схема OpenAPI описывает `detail` как массив ошибок. Фактический ответ на пустой выбор имеет статус 422 и строку `«Имеющиеся продукты: выберите хотя бы один продукт.»` в поле `detail`. Клиент, написанный по Swagger, будет ожидать другую структуру. [Обработчик ошибки](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/main.py#L55-L79) · [Описание маршрута](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/main.py#L139-L141)

**Предложение.** Описать модель ошибки со строковым полем `detail` и указать её для ответов 422 у соответствующих маршрутов. Проверить схему из `/openapi.json` и реальный ответ на один и тот же некорректный ввод.

<a name="r05"></a>

### R05. После смены продуктов может появиться подбор для прежнего выбора

Пока идёт запрос, пользователь может менять флажки. Обработчик изменения очищает результаты, но запоздавший ответ опять заполняет список. В проверке был отправлен запрос для молока, затем выбран другой продукт. После получения ответа на экране появился рецепт для молока. [Отправка запроса и вывод](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L163-L176) · [Обработчик смены выбора](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L179-L182)

**Предложение.** Отмечать каждый новый подбор номером, а при смене выбора или очистке результатов сбрасывать актуальность прежнего запроса. Перед выводом сверять номер. Проверить смену выбора до получения ответа.

<a name="r06"></a>

### R06. Завершение сохранения очищает уже открытый редактор другого рецепта

Пока сохраняется рецепт А, кнопки «Редактировать» на карточках остаются доступны. Можно открыть рецепт Б и начать править его. Когда приходит успешный ответ для А, вызов `resetEditor()` сбрасывает текущую форму вместе с правками Б. [Открытие редактора](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L90-L101) · [Сброс после сохранения](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L147-L159)

**Предложение.** На время сохранения блокировать поля редактора, отмену и переход к редактированию другого рецепта. Снимать блокировку и при успехе, и при ошибке. Проверить сценарий с задержанным ответом и убедиться, что при неуспешном сохранении введённый текст остаётся доступен.

<a name="r07"></a>

### R07. Сбой обновления списка выглядит как неудачное добавление продукта

Форма сначала отправляет `POST`, затем отдельным запросом загружает справочник. Если запись создана, но второй запрос завершается с ошибкой, форма остаётся заполненной и сообщает о проблеме со связью. Повторное нажатие отправляет тот же продукт и получает 409. [Отправка формы продукта](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L134-L144)

**Предложение.** После ответа 201 отметить продукт как добавленный и очистить поле. При сбое обновления показать сообщение «Продукт добавлен. Обновить список?» и повторять только чтение справочника. Проверить последовательность 201 → сбой чтения → повтор чтения.

<a name="r08"></a>

### R08. Текстовая ошибка сервера превращается в сообщение парсера JSON

При любом неуспешном HTTP-ответе интерфейс сразу вызывает `response.json()`. Когда ответ 503 содержал обычный текст, в поле статуса появилось английское сообщение парсера, а предусмотренное русское пояснение не отобразилось. [Чтение тела ответа](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L17-L24) · [Вывод сообщения](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L122-L131)

**Предложение.** Безопасно извлекать строковый `detail`, когда тело удалось прочитать как JSON. Для пустого или текстового тела показывать понятное сообщение со статусом HTTP. Проверить стандартную ошибку 422 и текстовый ответ 503.

## Рекомендательные

<a name="r09"></a>

### R09. Полное совпадение отображается как «Не хватает: всё есть»

Даже при пустом списке недостающих продуктов интерфейс добавляет подпись «Не хватает». Так пользователь видит противоречивый текст рядом со 100% совпадением. [Формирование карточки результата](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/app/static/app.js#L170-L176)

**Предложение.** Для пустого списка выводить «Все ингредиенты есть». Подпись «Не хватает» оставить для непустого списка. Проверить карточки для полного и частичного совпадения.

<a name="r10"></a>

### R10. Тест страницы проверяет загрузку JavaScript, но не действия пользователя

Автотест получает главную страницу и файл скрипта со статусом 200. Он останется зелёным, даже если нажатие «Подобрать рецепты» перестанет показывать результат. API-тесты проверяют данные отдельно от интерфейса. [Тест статических страниц](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/tests/test_api.py#L4-L10) · [Тест API подбора](https://github.com/nekentoss/what-to-cook/blob/b4d4f90f1a47c4327be4111d1e7a94d44a94069c/tests/test_api.py#L108-L121)

**Предложение.** Добавить один браузерный тест с отдельной тестовой базой. Выбрать продукт, нажать кнопку подбора и проверить видимые название рецепта, процент и недостающий ингредиент. Для начала достаточно одного сквозного сценария.

## Что проверено

- На исходном коде MVP прошли все 42 теста. Для R01–R04 дополнительно использовались временные базы SQLite. В R01 проверялся повтор ID и чтение по старому адресу. Последствие для кнопки удаления установлено по обработчику карточки.
- Для R02 считались загрузки объектов `Recipe` в сессию SQLAlchemy во время одного запроса. Время выполнения не измерялось.
- Для R05–R09 обработчики исходного `app.js` запускались в Node.js с имитацией элементов страницы и ответов сервера. Для R10 изучены тесты в репозитории. Браузерный сценарий в этом ревью не запускался.
